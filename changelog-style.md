# Changelog and code comment style

Concrete rules for Linux kernel commit messages and source comments, distilled from hand-written commits 2012–2026 and maintainer edits of AI drafts. Load this when you are writing or reviewing a patch changelog or adding comments. For code structure rules (helpers, function length, early return) see `kernel-style.md` §3. For principles behind the rules see `kernel-readability-principles.md`. For LLM tells checklist see `llm-tells-checklist.md`.

## 0. Factual integrity — never invent, always verify
Canonical: [](./kernel-style.md#0-factual-integrity--never-invent-always-verify) (R0-1..R0-6) per CONTRIBUTING §2 one-source-of-truth. This section is non-canonical summary + changelog-specific tool pointers only.

- See canonical R0-1..R0-6 in kernel-style.md. In changelog context additionally:
- <!-- R0-3-CH --> Verify scope, files touched, symptom, root cause, fix mechanism, performance delta, `Fixes:` hash, `Link:` URL, `Reported-by:` name against diff this session — not from memory. A number you derived rather than measured is worse than no number: a reviewer cannot check it and you cannot defend it.
- <!-- R0-5-CH --> Paste raw artifact verbatim: oops splat, benchmark table, `git log --oneline`, `perf stat` — literal block then explanation. Checks: `git show <hash>` exists, lore/syzbot link resolves.
- <!-- R0-6-CH --> Pre-write verification gate: run `/kreview` (setup in [review-prompts.md](./review-prompts.md)), the reviewed kernel tree's `scripts/checkpatch.pl`, `git log --oneline -- <path>`, benchmark, then write. Treat unverified prose as bug on par with wrong code. CI helper: `scripts/lint-changelog.py` checks paragraph caps, Fixes+Cc pairing, banned phrases.

## 1. Changelog / commit message
- <!-- CL-10 --> **Subject: `subsystem: lowercase imperative summary`.** Lowercase after the colon, no trailing period, imperative mood. (e.g. `1aa43598c03b` "mm: remove unnecessary calls to lru_add_drain"; `434247637c66` "bpf: use kvzmalloc to allocate BPF verifier environment"). x86/tip commits capitalize the first word per maintainer convention (e.g. `209954cbc7d0` "x86/mm/tlb: Update mm_cpumask lazily") — match the subsystem's existing style, not a fixed rule.
- <!-- CL-10b --> **Check git history for prevailing subject prefix before choosing yours.** Run `git log --oneline -- <path>` or `git log --oneline --grep <subsystem>` to see what prefix prior commits touching that file actually use, and match it. Do not invent new subsystem token when established one exists — e.g. `kernel/trace/fprobe.c` history uses `tracing/fprobe:` or `fprobe:`, never `trace/fprobe:`, so use prevailing form even if directory is `kernel/trace/`. Consistency across history matters more than literal directory name.
- <!-- CL-10c --> **Use comma-joined multi-subsystem prefixes when a change spans areas.** A common habit: `mm,vmscan:`, `ipc,sem:`, `mm,thp,shmem:`, `mm,madvise,hugetlb:` — no space after commas. (e.g. `8ebe0a5eaaeb`, `da27f796a832`).
- <!-- CL-10d --> **Subject must reflect primary impact, not cleanup label.** If change fixes race, queue stop, data loss, corruption, don't hide as "track credits" or "cleanup". Rephrase to "fix blocked-ring race permanently stopping queue" per Arend van Spriel `<d5b7a4a8-532f-47c7-a883-036d5cc81a90@broadcom.com>` brcm80211 2026-07-31. Subject describes what code does after patch, not that it fixes.
- <!-- CL-10e --> **Prefer a subject that names what the code now does, not what it stopped doing, when a positive form exists.** Test: can you name the behaviour after the patch in about the same words? If yes, that is the subject. The negative form earns its place when the removed behaviour *is* the point and no positive form names it — a leak, a spurious warning, a write that should never have happened: `drbd: don't leak the shared secret to unprivileged netlink dumps`, `iomap: don't free integrity payload that doesn't exist`. Preference, not ban.
- <!-- CL-10f --> **Sample the touched file's history for body idiom, not just the subject prefix.** After CL-10b picks the prefix, `git show` two or three commits by different authors that touched the same file — never only the current series' own patches — and match their terminology and tone. Length is measured, not sampled: read the file's envelope (`git log --format=%B -20 -- <path>`) and include one sample of your patch's size and kind — length follows change size (CL-24). (e.g. `90d79f4b97e9` speaks in `PB_has_kernel`, `nr_content_blocks`, and `gigablock` — the names its own diff introduces — in six tight paragraphs.) A body that uses generic language where the subsystem has names reads foreign.

- <!-- CL-12b --> **When the word cap and one idea per paragraph disagree, the idea wins.** A paragraph carrying one idea in under 70 words is finished; splitting it further to reach a lower number makes the changelog worse. The 70-word line stays hard, because one idea needing more than 70 words is usually two.
- <!-- CL-20 --> **Open the body with the problem or current behavior in plain present tense.** State what the code does today and why that's wrong, before the fix. (e.g. `e9868505987a`; `32d4f4b782bb` opens by naming the offending commit and the bug it introduced).
- <!-- CL-21 --> **Keep verb tense consistent — describe the code's current behavior in the present throughout.** If the code does X today, write "copies", "does so", "turns" — don't drift into past tense ("did so") mid-paragraph, and don't call the present code the "original" version (say "the call site"/"here", not "the original call site"). Mixing tenses makes a reviewer unsure whether you mean current behavior or history.
- <!-- CL-22 --> **Lead a bugfix with the real-world scenario and user-visible symptom, not the code mechanism.** Say who triggers it and what breaks, then descend into internals. (e.g. `2820b0f09be9` opens "Malloc libraries, like jemalloc and tcalloc, take decisions on when to call madvise.." and builds to a SIGBUS kill — it does NOT open with "zap_page_range_single fails to take i_mmap_rwsem"). State the worst credible user-visible case — hang, crash, DoS, corruption, disclosure — calibrated to its proof: observed, possible-but-unproven, or not established. (Morton on page_vma_mapped: hangs/crashes/DoS credible; corruption possible but unproven; disclosure not established.) Each effect claimed here needs its proof leg under CL-27.
- <!-- CL-46 --> **Keep the impact, with few numbers.** State what users hit: one sentence and one figure per effect — stable maintainers and backporters need it. Keep it even when a reviewer's rewrite drops it; averages, ranges, and per-configuration results go in a reply when asked.
- <!-- CL-23 --> **For a race, draw the interleaving as an ASCII `CPU 1 / CPU 2` diagram.** A common device. (e.g. `2820b0f09be9`). Draw one only when the bug is the order of steps by two or more actors — a loop missing one exit check needs none. A legend names every actor, CPU, and lock first; setup runs as a step, never as implicit initial state. Diagrams may run to 100 columns for legibility; accept the checkpatch width warning on diagrams (Zijlstra's own `b6e13e85829f` runs to 92).
- <!-- CL-24 --> **Match changelog length to change size.** A simple improvement gets ~3 tight paragraphs; don't walk through every code path. Bug fixes with a subtle race earn more. (e.g. `efa7df3e3bb5` is 3 short paragraphs — lead with the action "Align larger anonymous mappings..", then the qualitative benefit "better TLB hit rates and execution time", no path-by-path breakdown).
- **For a simple improvement, leading with the action then the benefit is fine** (problem-first is for bug fixes). (e.g. `efa7df3e3bb5`).
- <!-- CL-25 --> **Structure: problem → cause → fix → effect, as short prose paragraphs.** Typically 3–6 paragraphs of 2–4 sentences each. The fix paragraph often starts with the imperative verb ("Avoid the softlockup..", "Take the hugetlb_lock before.."). (e.g. `5cbcb62dddf5`, `12df140f0bdf`).
- <!-- CL-48 --> **A feature message runs need → design → API → tests.** Say what the feature is for, then how it works, then the interface it adds, then what the tests cover and their result. There is no "Fix this by ..." and no bug impact to keep. Size the message to the change the way CL-24 sizes a fix: a new subsystem earns more than a one-line addition, but split and simplify technical content rather than cutting it.
- <!-- CL-26 --> **Explain WHY far more than WHAT; justify with data, repro, or reasoning.** Quantify the effect with real numbers when available — before/after tables, percentages, timings. Describe a removal by what it buys, with a number, not as an absence: "remove SLAB_HWCACHE_ALIGN to pack 4 iova structs in a cache line", not "no longer needs SLAB_HWCACHE_ALIGN". (e.g. `e1e4cfd01a6e` throughput table 1560→4720 MB/s; `209954cbc7d0` "Before: ~4.5s After: ~4.2s"; `da27f796a832` "from 6 minutes, to a little over 1 second").
- <!-- CL-66 --> **Measurements read as sentences, not labels.** A bare metric plus two numbers is a label, not information — the reader should never need the test file open to know whether the numbers are good. Rewrite as three clauses: what was compared, the bar it had to clear, the result ("the grid's numbers match the old path to within 0.00006, far inside the 0.01 the suite allows"). Keep the exact figures; translate only the frame. Upstream text always gets the sentence; code comments may keep the terse form where the suite next door defines the terms.
- <!-- CL-26b --> **More about motivations than implementation details.** Lead with why old behavior was costly — user-visible symptom, spec violation, regression, or risk — not how you fixed it. Say what now happens for users or hardware, not what diff already shows. For a design tradeoff, name the cost accepted and the assumption behind it, not the arithmetic the diff already shows.
- <!-- CL-27 --> **Paste the raw artifact verbatim; don't just describe it.** Show the actual oops/WARNING/splat with call trace, the reproducer command, or a before/after benchmark table — indented as a literal block — then explain it below. For a complex splat, annotate it with `1)` `2)` `3)` markers the prose refers to, or add `// file:line` comments at end of call trace lines as a clarifying aid provided the original function+offset text is preserved verbatim — line number annotations are allowed because they help reviewers navigate source without changing artifact meaning. Letting the reviewer see what you saw lets them verify the fix without the thread. (composite: Dan Williams `101c268bd2f3` annotated splat; Mel Gorman `09a913a7a947` benchmark table; Breno Leitao `62adf8c290f2` `time` before/after.) Every effect the changelog claims — including each rung of the CL-22 worst case — needs a proof leg: a pasted log line, a reproducer with before/after results, or a code-trace walk through file:function showing the path is reachable. An effect with no leg drops to "possible but unproven" or is cut; unproven claims are hedged, never asserted.
- <!-- CL-32 --> **When a series splits one optimisation across several patches, give each patch its own table measured from the series base, and say which patch owns which column.** One combined table on the last patch credits it with the earlier patches' work: a walk-restructuring patch worth 2.3x on base pages followed by a refcount-batching patch reads as if batching produced both. Measure with the series applied up to and including the patch being described, keep `before` at the base for every table so the columns are comparable, and name in prose the result that belongs to an earlier patch and is unchanged here. The decomposition is usually the more interesting result — a combined 14.5x hid that two thirds of the mechanism helped every page size, not just large folios. Fix the table before filling it: same axes, same conditions for every candidate. A table whose shape shifts per candidate hides the comparison it claims to show.
- <!-- CL-52 --> **State the math each path uses and which side diverged.** When two paths should agree and do not — proposer/verifier, batched/sequential, writer/reader — the message names what each side computes (one accumulator versus four-plus-reduce, single-row versus batched) and which side the evidence convicts, so the reviewer stares at one path, not two.
- <!-- CL-53 --> **Results are a setup sentence plus a table, never a wall of prose.** At most two sentences of setup — what ran, on what rig, under what config — then a table whose rows are the conditions and whose columns are the metrics. Name the rig in external terms only: public hardware names plus context, quant, and concurrency, never an internal host, path, or script name. Table labels are external text too: a row or column named for a rig phase means nothing to a reviewer who never ran the rig, so rename it to the plain thing it measures or define it in the setup sentence.

- <!-- CL-33 --> **Report a difference inside run-to-run variation as unchanged, and keep the rows that show the mechanism did not fire.** A 1.7% move between two boots is not a win to claim or a regression to confess; write "unchanged" and let the number stand beside it. Rows where nothing should have changed are evidence, not filler: a control size that stays flat is what shows the new path was not entered, and a reader who cannot see it has to take the scope claim on trust.
- <!-- CL-65 --> **Counts that cover post-gate pages say which gate excluded the rest.** A number that counts only what passed an earlier per-page gate looks bogus to a reader who assumes every member was equally sensitive. Name the gate that already vetted the excluded members, or the count reads as arbitrary. Test: if re-running without that gate changes the count by the number of gate-handled members, say so in the same breath — a bare "15 faults" with no gate named invites "why not 16".
- <!-- CL-50 --> **Never apologize for unfinished numbers; specify the re-run.** When the message's numbers are not yet accurate, state the exact re-run that produces accurate ones — the command, the tree, the config — so a reviewer can run it rather than forgive the gap. An apology asks for trust; a re-run spec earns checking.
- <!-- CL-51 --> **A killed, timed-out, or clipped run is a lower bound, never a value.** If the run did not finish, its result shows at most what was reached, not what the code does. Report it as "at least X before the run was stopped at Y" — or drop it. A clipped output presented as the measurement invents a ceiling the run never established.
- <!-- CL-45 --> **Say what bounds a number, not just its value.** A maximum seen in testing is reported as "in testing", never as the code's limit. When a figure equals a default, period, or timeout, name that cause — the message says what stops the spin, not how long it lasted in our runs.

- <!-- CL-35 --> **Expect several passes, and compress in place before deleting paragraphs.** A first draft describes what the code does; later passes trade mechanism for the reasoning behind it. Keep going while a pass still changes what the changelog claims: a pass changed only wording if every number, name, cost and assumption in the new text was already in the old, and none went missing. When shortening, trim words inside paragraphs before deleting any: deleting one loses a distinct claim, rewriting it does not. CL-25's "3-6 paragraphs" is a shape hint, not a cut target.
- <!-- CL-36 --> **An "unchanged" sentence stays when it bounds review scope, goes when it is comparative reassurance.** "The rcache layer is unchanged. It deals in raw pfn values" tells a reviewer which adjacent layer they need not audit. "These calls were O(log n) already and stay that way" reassures about something the diff never threatened. For a deletion, keep the causal link that justifies it, drop the tutorial on the mechanism behind it. When a maintainer says "cut what stays the same", they mean the reassurance. The same test applies to proof paragraphs, not just sentences: a paragraph arguing that an untouched case stays correct — a type the helper cannot return, a conversion the table cannot list — goes; the diff is the proof.
- <!-- CL-37 --> **When several reasons support one choice, lead with the one that makes the alternative impossible.** Put the hard constraint first and compress the rest to a clause. A reason that makes the alternative merely awkward, placed first, reads as the whole justification and invites the reviewer to propose the alternative anyway.
- <!-- CL-38 --> **Numbers in a changelog are problem-scale, effect, or safety — nothing else.** Keep the count that sizes the problem, the table that shows the effect, and the stall counts that show nothing broke. Cut internal ratios (how often path A fires versus path B), tried-and-dropped experiment counts, and mechanism telemetry — that evidence stays in local notes, citable on request. A ratio that survives carries its scope in the same breath: backend, dtype, phase. An unscoped "-16%" reads as global.
- <!-- CL-47 --> **Say how each claim was established.** A claim is measured, reproduced, or found by reading — and the message says which. A claim found by reading alone gets "would" ("the waiter would dereference the poison"). Name the configuration each result needs: the option the bug needs, not just the subsystem it lives in.
- <!-- CL-64 --> **"Mixed" names its dimension.** When a batch, run, or group is "mixed", name the varying property in plain words in the same breath ("some pages are exclusive, some are not") and state outcomes with concrete actors and plain verbs — never insider verbs like "drains its queue" standing in for who does what to which structure. A compound adjective like "mixed-exclusivity" reads precise but forces the reader to guess which property varies. Test: delete the compound — if the sentence still says the same thing, keep the deletion; if the plain version needs the compound to stay short, the sentence describes two properties at once — split them.
- <!-- CL-67 --> **Translate every mechanism term in place; state the unit and do the arithmetic.** When the unit of storage is ambiguous (blocks versus pages versus extents), state the unit and do the scale arithmetic in the same breath ("64 blocks per extent, so a 1M-block filesystem is about 15,625 extents and about 6GB of metadata") — that sentence is what stops the cold reader inventing 1M individual entries. No term appears unexplained on first use; no metaphor survives when a plain version says the same thing. Test: read the message aloud cold on a phone. Keep it tight: the plain version must not be longer than the dense version it replaces.
- <!-- CL-49 --> **Every name cited in the message must exist in the code, the tests, or the series.** Check each one: the test cases the message names exist, the subjects it cites match the other patches. When a subject changes, update every patch and cover letter that cites it. Comments drift — one array named `t[i]` and `l[i]` was `depth_t` and `depth_l`; one handler said "open() and read() alone" but also calls close().
- <!-- CL-56 --> **Caller claims cover every caller; escalation paragraphs name the state change.** "The caller checked the head" is false if any caller checks nothing — and a loop starting at the head exists precisely because of that caller. Never narrate a disagreement the code makes impossible: if a lookup and a trim check the same page under the same held lock, they cannot disagree. And a "worse, X can happen" paragraph must name the state change between the two points that makes the worse outcome possible — if nothing is consumed between lookup 1 and lookup 2, lookup 2 cannot fail where lookup 1 succeeded, and the paragraph goes.
- <!-- CL-57 --> **Probe the structural property at HEAD before writing the why.** When the why paragraph argues a structural property — exclusive versus inclusive, disjoint tiers, superset — verify it on the tree first: store, promote or load, then assert state on both tiers. An unprobed structural claim is a guess with a paragraph around it.
- <!-- CL-58 --> **No dangling otherwise: restate the condition.** A sentence opening with "otherwise", "instead", or any bare contrast restates the condition it points at ("On non-CUDA systems, allocate ..." not "Otherwise allocate ..."). Test: read the sentence alone, out of the message. If it doesn't parse standalone, restate what "otherwise" points at.
- <!-- CL-59 --> **Articles claim identity: "a" versus "the same".** "The same X" asserts identity with something already named — use it only when the referent is literally the same object. A new allocation, mapping, or copy is "a X", never "the same X" — the definite article smuggles in a sameness the code does not provide. Test: point at the antecedent of "the same"; no antecedent, use "a".
- <!-- CL-60 --> **The measurement rig is setup, never a dependency.** The hardware, firmware, toolchain, or local harness used to produce the numbers are the rig: they are named in the setup sentences, never as "depends on", "stacked on", or "requires". Dependencies are only code the feature needs to build or run — an upstream user must not need your harness to use the feature. Test: delete the local stack — if the feature still builds and its tests still pass, it was rig, however essential it was to your numbers.
- <!-- CL-40 --> **Name the condition the code keys off, not the witness that triggered it.** When the code branches on a generic predicate, prose, comments, and identifiers use the generic condition — never the specific platform or instance that happened to trigger it. A scope sentence stays true for the next platform that satisfies the same predicate; one written around the witness reads foreign there. The witness may stay as a concrete example or error string, but scope sentences must survive substitution: replace the witness with a different satisfier of the condition — if the sentence reads false, rename to the condition.
- <!-- CL-44 --> **State the design intent before the missed case.** When the bug is a gap in what the code assumed, say why the code is built that way first, then the case it missed — the fix then reads as the obvious one. Read the changelog of the commit in `Fixes:` before writing; it usually states the intent (e.g. `992caf7f1724` states why the rtmutex spin exists, `6467822b8cc9` why the PREEMPT_RT chain walk ignores ww_mutex cycles). Never invent intent the commit, its comments, or its author do not state.
- <!-- CL-41 --> **State the invariant before the mechanism.** After the problem, name the truth the change establishes and why that truth eliminates the problem — before any mechanism text. If the message cannot state the invariant, the change is not understood yet. A reader who stops after this paragraph knows what is wrong and what fixes it; mechanism paragraphs that follow carry only rationale, since reviewers read code.
- <!-- CL-42 --> **Permanent text describes what is true now, never what the old code did.** Comments and changelog bodies state the present invariant, not the history: no "as before", "used to", "previously", "the old code". A future reader cannot reconstruct the history, and if the history mattered it lives in the log — the comment carries the contract a reader can verify against the current tree. Rewrite to the rule that makes the present code right.
- <!-- CL-39 --> **A one-sided rule gets a reverse-direction sentence.** When a patch restricts one direction of a symmetric policy, say in one sentence why the reverse needs no such rule — the reader's next question, answered before it is asked.
- <!-- CL-28 --> **If the bug produces a kernel message, the changelog MUST include it verbatim.** For any bugfix where the kernel emits a message — KASAN/UBSAN/KFENCE report, `WARNING:`/`BUG:`, oops splat, `INFO: task hung`/soft-lockup/RCU-stall, lockdep splat, `kmemleak` unreferenced-object dump, `Call Trace` — paste the real message as an indented literal block, then explain it. Prose that only names or paraphrases the symptom ("triggers a slab-use-after-free in __up_read") is not enough; the reviewer must see the literal report. Trim register/hex-dump/memory-state noise if long, but keep the signature line, the crashing `Call Trace`, and (for UAF) the Allocated-by/Freed-by stacks. Do not embed a message you did not capture this session — if you only have a different signature than the one your prose describes, paste what you have and reconcile the prose, never fabricate the matching splat (rule 0).
- **Bound the scope and name your own weaknesses.** State explicitly what the patch does NOT do, and call out any remaining weakness, limitation, or small regression before a reviewer finds it ("the keen reader will notice..", "the main weakness is.."). It builds trust and pre-empts review churn. (composite: Johannes Weiner `e3aa7df331bc`; Mel Gorman `8d58802fc9de`; Vlastimil Babka `fc0c8f9089c2`.)
- <!-- CL-63 --> **Bounds state the proven limit or the validation edge.** When a patch draws a boundary — size caps, shape gates, allow-lists — the message says which side of testing it sits on. A gate that exists because validation stopped there is written as such ("parity is proven at M in {1, 2, 6}; wider batches stay on the old path until re-validated"), never as architecture ("eligible calls take the fast path"). The reader must be able to tell a proven limit from an untested region — the fix for the first is redesign, for the second a test leg.
- <!-- CL-30 --> **For concurrency, locking, lifetime, bounds, and double-free fixes, add a safety paragraph.** After problem→cause→fix, explain why the fix should be safe: what lock protects the racing store, what lifetime or refcount prevents reuse, how TOCTOU is closed, or why allocation size now matches validation size. Name the lock or configfs semaphore (`down_write(&nvmet_config_sem)` deletes old controllers), the snapshot field (`ctrl->max_qid` immutable after creation), and what cannot race after the fix. Write "should be safe because..." not "is safe because...", since patches can overlook paths. This paragraph is intentionally verifiable in review — reviewers check the lock, snapshot, or free path you name. (example: nvmet `max_qid` fix `eae699c90e4b` paragraph: "This change should be safe because configfs qid_max store holds down_write(&nvmet_config_sem), updates subsys->max_qid, then deletes all existing controllers. New controllers snapshot the new value and allocate matching arrays. The snapshot in ctrl is immutable after creation, so no extra locking should be needed for readers.") For any suspected race claiming use-after-free via asynchronous work, build a refcount budget: enumerate every acquire that pins the shared pointer and every release on both sides, and prove with certainty that one side lacks the reference needed to keep the object alive at the claimed free point. If the cached pointer itself holds a pinning reference, the free is blocked until that reference is dropped — at most a prompt-reclaim or cgroup-removal stall, not a use-after-free. For a use that survives a lock or RCU drop, identify the logical owner and the pin that survives the drop. If the storage is permanently mapped or pooled, return-to-pool and reuse is a logical free even though the storage remains addressable and reads do not fault; distinguish read (reportable only when the stale value drives a decision) from write (always reportable because it corrupts the next owner's reuse of the same storage). Only a reference or other explicit pin held before the drop and released after the last use proves safety.
- <!-- CL-61 --> **Restoration needs no safety case.** When the patch restores pre-regression behavior, the prior shipping history is the safety argument: say what was restored and stop. Reserve the safety paragraph for patches that introduce behavior that never shipped — belaboring safety on a restoration signals an uncertainty the history already answers.
- <!-- CL-31 --> **For every syzkaller/syzbot fix, describe how the bug can happen and verify the chain.** If the report includes a reproducer, follow what the reproducer does in order, mapping each syscall/ioctl to kernel file:function. If there is no reproducer, build a concise chain of 2-4 sentences citing file:function per step: what can set flag or grow limit (e.g. `fbcon.c:fbcon_font_set` sets `hi_font_mask`, `configfs.c:attr_qid_max_store` grows `max_qid` under `down_write`), what retains stale data or old allocation (screen buffer retains glyph with high bit via `vt.c:screen_glyph`, controller keeps old small `sqs` array allocated in `core.c:nvmet_alloc_ctrl`), how buggy path differs from sister site that already checks (e.g. `bit_putcs_aligned()` at `18c4ef4e765a` clamps `ch >= charcount`, `bit_cursor()` does not; `nvmet_execute_io_connect()` validated live large but deref used old small array), and concrete OOB example (`qid=2` past 16-byte alloc, or glyph 257 past 256-glyph `fontdata_8x16+0x1010`). Keep under 70 words, one over-50 allowed. This chain is mandatory and kverify checks each file:function exists and that sister site indeed has the clamp.
- <!-- CL-54 --> **Open the mechanism paragraph with the tripwire.** When the defect is an early return that waves a class of callers past a check, the mechanism paragraph opens with the exact flag combination — and states that the downstream path is dead code for that class. A safety claim argued downstream of the tripwire is unverifiable; stated at the tripwire, the reviewer checks the gate instead of the whole path.
- <!-- CL-55 --> **Say which stage a check gates.** When a paragraph contrasts two paths and one of them "does not need" a check, state which stage the check gates — acquisition or the consumer's later use — and whether the consumer can still observe the attribute that was checked. A check at acquisition does not cover a consumer that re-observes; a check the consumer repeats does not cover acquisition.
- **Pre-empt the "why not fix it in the obvious place?" question.** When the fix could plausibly belong in a more obvious or upstream function, say in the changelog why that path does not or cannot handle the case (e.g. it is best-effort and can leave the bad state behind), so a reviewer does not have to ask.
- <!-- CL-29 --> **Write for human reviewers, not as semcode dump: narrative with transition phrasing.** Cite only 2-3 key file:function locations needed for kverify (enough to verify chain), not every line. One idea per paragraph per CL-12. At paragraph boundary where state changes, use explicit transition naming actor/event first: "When X is changed from A to B, ..." rather than dense "from previous X mode, while current Y...". This split improves kverify and readability and matches personal style saved in memory. Avoid mechanical listing like "does Y at file:line which does Z at file:line" repeated. Changelogs should read as story for upstream maintainers, not as tool output.
- <!-- CL-34 --> **Do not hallucinate any part of changelog from previous, unrelated fixes.** Every paragraph, sentence, and footer must describe only the bug fixed by this patch, verifiable from its diff and its associated bug report (syzkaller report, KASAN splat, reproducer). If a paragraph mentions a subsystem, call chain, reproducer, or report that belongs to a different, previous fix but this patch touches a different subsystem, it is leakage — delete and rewrite from scratch using only this patch's diff and report. This applies to all footers including Fixes:, Closes:, Reported-by:, Link:: each must name a commit or report that this patch actually fixes; a Fixes: hash must exist via `git show`, a Closes:/Link: URL must resolve and be for this bug. Hallucinated footers or leaked paragraphs are HIGH/MISLEADING. Confirm trailer form with `git interpret-trailers --parse`, and cite in-body commits as `commit <12-char sha> ("subject")` on one line.

- <!-- CL-14 --> <!-- CL-14-CH --> **Write for the upstream audience, not your internal tooling.** A changelog is read by maintainers who have never seen your CI dashboard, internal bot nicknames, private branch names, or vendor ticket systems. Include only information that helps an upstream reviewer understand, reproduce, and verify the fix. Strip internal identifiers that carry no meaning outside your environment — internal agent or bot nicknames ("analyzed by internal-agent-1"), internal syzkaller or CI bucket hashes without a public syzkaller or syzbot link, internal git branch names (`internal-fixes-2026-07-15`), internal hostnames, PIDs from private test runs unless they illustrate the bug mechanism, build IDs from private trees, Phabricator or Jira IDs, etc. Replace them with generic, reproducible descriptions: "syzkaller triggers..", "KASAN reports..", "reproducer available at syzbot <link>..", "tested on v6.15-rc1". Code comments get even less context than changelogs — never mention internal dashboards, bucket IDs, or agent names in source; put that in the commit message if at all, and even there prefer generic.
- **State the reason once; don't sell the change or re-argue it.** Give the rationale plainly, a single time — never argue that the change is good, that the old form "reads oddly," or reorder a later, otherwise-neutral section (e.g. benchmark results) just to lean on a point already made. (Cut from the get_user_page_lookup_vma rename: "The 'remote' in the name describes the mm, not what the helper does, and reads oddly next to get_user_pages_remote(). Name it for its action.")

(edit of AI draft, get_user_page_vma series 2026)
- **One idea per paragraph; break a running block apart.** The problem, the "existing API doesn't fit" note, and the resulting behavior each get their own short paragraph rather than one dense block. (edit of AI draft, same series)
- <!-- CL-12 --> **Cap paragraph length: at most one paragraph may exceed 50 words, and none may exceed 70.** The one allowance is for content that genuinely cannot be split; a second over-long paragraph means the changelog wants restructuring, not a longer allowance. Applies to both changelogs and code comments. A checkable backstop for "one idea per paragraph": a paragraph over the limit is a signal to split it, not to pad it to 70.
- **Merging two related clauses under the cap beats splitting them just to satisfy "one idea per paragraph."** A paragraph break has a real cost — the next paragraph re-establishes subject and context from scratch — so only pay it when the cap forces it or the two halves are genuinely separate, independently-verifiable claims. If two adjacent short paragraphs still fit under 50 words joined by a connective (since, so, then, --), join them; that is the shorter form, not a less clear one.
- **Before finalizing, run a compression pass over the whole changelog, checking each paragraph against three questions.** (1) Does it restate what a code comment added or touched by the same diff already says? If so, cut it to nothing or a single clause — the reviewer has the comment right there. (2) Does it gloss an already-obvious value (a sentinel, an enum, a self-explanatory name) by restating its meaning in English? Cut the gloss. (3) Do two adjacent paragraphs describe sequential sub-steps of the same single change that a connective could join under the cap? Join them. What survives this pass should be only the paragraphs carrying a genuinely distinct, independently-verifiable claim — a correctness nuance, a safety argument, a separately-measured effect — that a reviewer needs to check on its own; don't merge those away just to hit a length target.
- **Forward-reference a later patch for purpose, not status, and name what you are pointing at.** Keep "cleans up the name space for adding a get_user_page_vma() variant" (why the patch exists); drop "no caller uses it yet; switched to it in the next patch" (bookkeeping the reader already sees). "A later change needs the same three lines" is purpose-shaped and still useless: it names neither the change nor the lines, so in the committed log it points at nothing. Name the function, helper, or contract the later patch introduces.
- **Justify a prep patch on its own terms; never describe a later patch's behavior as this patch's motivation.** Open with the problem that exists *now*, in present tense, the way the accepted x86 sibling does ("__access_remote_vm() reads another process's memory under the mmap lock .. that lock is contended"), not with what a follow-up will do ("Later in this series __access_remote_vm() untags the remote address without holding the mmap lock"). At the prep patch that later behavior does not exist yet, so stating it as the reason misleads a reviewer reading the patch in order. Forward-reference the later patch only for purpose (why the helper is added), never as if it were current behavior.
- <!-- CL-62 --> **Impact paragraphs claim only what this commit's tree makes true.** A user-visible opening must be verifiable at the commit it sits on. A new op with no in-tree caller "adds the op for callers to use" — never "all callers now take this path" or "all batches run through X". Effect sentences need a caller in the diff; without one they overclaim even when the caller is planned next. Test: git grep at the tip for a caller of the new symbol — none found, no claim.
- <!-- CL-68 --> **Ship only what the commit contains; follow-ups it lacks get no announcement.** A promise adds no information: it commits to nothing, and the reviewer reads it as scope being smuggled in. If the follow-up is real work with a gate, state it as a limit with its gate; if it isn't, it doesn't go in the message. Test: delete the sentence — if nothing the reviewer needs is lost, keep it deleted. The one exception is a follow-up that is literally the next commit in the same series: naming it as its own paragraph ("A follow-up commit makes this path asynchronous") is series routing, not a promise — keep it unconditional and in its own paragraph, never folded into a limit sentence.

## 2. Code comments
- **Comment the WHY: hardware behavior, locking, ordering, lifetime, subtle invariants — never restate the code.** (e.g. `b7aa05cbdc52` INVLPGB ordering/flag semantics; `209954cbc7d0` "Atomic writes to mm_cpumask can be expensive under contention. The CPU will be removed lazily at TLB flush time.").
- <!-- CC-10b --> **A sentence describing what the function does with its arguments is restatement, even when it reads like an explanation.** The signature and the body already say it. Comment the constraint that made the function necessary instead: "A maple tree cannot hold overlapping ranges, so overlapping reservations have to be merged into one wider entry" beats "Widen [*lo, *hi] to cover every iova overlapping the requested range, or return the existing iova if that one already covers the whole request."
- **Density is low and purposeful.** Most lines uncommented; comments cluster where reasoning is non-obvious (a new helper, a tricky branch, a race). Obvious code gets none.
- **Keep a comment as short as the point allows — one or two lines for a simple invariant, not a paragraph.** Even when every line is accurate, padding an obvious placement/ordering rule into a multi-line explanation reads as LLM slop. Say the why in the fewest words and stop.
- **Same paragraph cap as changelogs: CL-12.**
- **For multi-branch helpers, give each branch a one-line rationale.** (e.g. `6db2526c1d69` `should_flush_tlb()`: "/* Lazy TLB will get flushed at the next context switch. */", "/* No mm means kernel memory flush. */", "/* In cpumask, but not the loaded mm? Periodically remove by flushing. */").
- **Break up very large conditionals and comment each outcome.** Lorenzo v2 14/33: "Break up the existing very large conditional, add comments and use.." (Message-ID 20260710-b4-pre-scalable-cow-v2-14-2a5aa403d977@kernel.org 2026-07-10). Prefer early return or helper split over dense if-else chains.
- **ASCII diagrams welcome for complex range or state adjustments, under 60 columns plain ASCII.** Lorenzo v2 15/33: "Add comments with ASCII diagrams to describe what we're doing" (Message-ID 20260710-b4-pre-scalable-cow-v2-15-2a5aa403d977@kernel.org). No Unicode box drawing.
- **Cross-reference other comments rather than duplicate explanation.** Lorenzo v2 17/33: "We refer the reader to the comment for vma_start_pgoff() so we don't.." (Message-ID 20260710-b4-pre-scalable-cow-v2-17-2a5aa403d977@kernel.org). One source of truth per invariant.
- **Improve comment language opportunistically when touching code, keep it concise.** Lorenzo v2 30/33: "While we're here, slightly improve the language of the comment describing" (Message-ID 20260710-b4-pre-scalable-cow-v2-30-2a5aa403d977@kernel.org).
- **Block comments above the function/decl; short notes inline or just above the line.** Full sentences, capitalized, ending with a period. (e.g. `f35b5d7d676e` "/* Ensures that larger anonymous mappings are THP aligned. */").
- **Document at the definition, not the declaration.** A bare prototype in a `.h` gets no descriptive comment — put the explanation in a block comment above the function body in the `.c` file, so there is one source of truth that cannot drift out of sync with the code. (Kerneldoc `/** */` for an exported API is the deliberate exception, and even that lives above the definition, not the prototype.)
- <!-- CC-12 --> **Plain why-block or nothing on static internal helpers; reserve `/**` for exported APIs.** A plain block carrying `@param:` restates the signature just as much — the scaffolding is what costs, not the marker. `lint-code.py` flags `@param` under a static.
- **Code comments are for upstream readers too — no internal identifiers in source.** Never mention internal dashboards, CI bucket hashes, agent or bot nicknames, private branch names, internal hostnames, or vendor ticket IDs in a `/* */` or `//` comment. Those rot the moment code leaves your tree and confuse reviewers who lack that context. Put operational provenance in the commit message if needed, and even there prefer generic phrasing per the changelog audience rule above.
- **Block comments are typically 2–8 lines of plain wrapped prose**, occasionally with a worded example list. (e.g. `b7aa05cbdc52`).
- **Personality is allowed in comments when it conveys real information.** (e.g. `b7aa05cbdc52` "/* Some compilers (I'm looking at you clang!) simply can't do DCE */").
- **Introduce a new helper by relating it to the family it resembles, then name the one key difference.** Orients a kernel reader faster than describing the mechanics from scratch. (Prefer "Simplified get_user_page* loop, which only walks page tables because we already have the VMA" over a from-scratch "walks the tables with follow_page_mask() and faults one in…"; get_user_page_vma doc comment 2026)
- **State why the code does things the way it does, not the alternative it replaced.** A comment saying a loop does X "instead of restarting the walk at each boundary" asks the reader to already hold a design in mind that no longer exists to read. Say why the shape is this way and, if needed, why it is safe; save "why this beats what came before" for the changelog, which is inherently a before/after document. (Cut from a loop comment that implicitly compared against a removed per-call design: "Walk every PTE from @address to @end" replaced "...in one call, instead of restarting the walk... at each folio boundary.")
- **Reach for an established systems-programming term for a common pattern instead of re-describing the mechanism, and name the specific function that completes the other half of the contract.** "Short read" (return fewer than requested, non-error, caller retries) says in two words what a bespoke description takes a sentence to say, and naming the actual function makes the claim checkable. Prefer "a failure partway through results in a short read; __get_user_pages() retrying the read will get the error" over "the walk stops and returns what it has; the caller re-issues from there."
- <!-- CC-10c --> **Once a decision is made, the comment records what a reader must know; the argument for it belongs in the changelog.** A comment sits where someone is trying to find out what the code does, and persuasion there costs them the answer. Keep the fact that constrains the code — a measured cost, an invariant, something the language will not allow — and drop the case for the choice, the restated consequence, and the closing flourish. "Do not write a database version. Part of the database was updated here, but other parts could have been written by an older version" beats the same point argued over five lines and ending on a line written to convince. This is CL-10e one level down: a subject names what the code does rather than what it stopped doing, and a comment states the contract rather than defending it.

- <!-- CC-10d --> **A code comment must not refer to the change that introduced it.** "This series", "this patch", "the commit that added this" are all true for about a week. Code outlives the series, and a reader in a year has no way to find what "this series" meant. Say the thing itself, or put it in the changelog where the reference resolves forever. `lint-code.py` flags these.

- <!-- CC-10e --> **Match the comment idiom of the code you are touching.** Sample the file's history — `git log -p -- <path>`, commits by different authors, not just the current series — before writing a comment: match their density, terminology, and tone within the caps this file sets. Shape is categorical — the samples settle one-liner vs block; block length is not, and follows the change being annotated — take the range from the file's own comments, and sample up when your samples disagree. (e.g. `6db2526c1d69` adds one-line per-branch rationales in `should_flush_tlb()`; `b7aa05cbdc52` adds a 2-8 line block with a personality aside.) A comment matching the file's idiom reads native; the same words dropped where the file comments differently read foreign.
- <!-- CC-10f --> **Policy branches carry the policy and its reason; mechanism facts move to the changelog.** A branch enforcing a placement or ordering policy says what is forbidden and why ("Do not allow X; that could break Y"), not the mechanism the code already shows (table order, which list is empty). The mechanism facts belong in the changelog, where the before/after comparison lives.
- <!-- CC-10g --> **When code relies on an earlier early-return, the comment names the exclusion.** If a check is absent because an earlier guard already returned for that case, say so at the relying site ("Partial blocks returned above, so reaching here means a whole block") — otherwise the missing check reads as a bug.
- <!-- CC-10h --> **A multi-line block comment opens with a bare `/*` line and closes with `*/` on its own line.** One ` * `-prefixed line per text line between them — never text on the opener with the rest wrapped below, never the closer riding up onto the last line. Text that fits on one line stays `/* ... */`.
- <!-- CC-15 --> **Simplify the code to the equivalent form that needs no explanation.** When the comment explaining tricky code confuses its first reader, simplify the code to the equivalent form — proved equivalent over the input range — then comment that form. Never explain around complexity you can delete.
- <!-- CC-16 --> **Interface comments answer: who creates, who consumes, how completion is observed.** A struct-ops or interface comment names the creator, the consumers, and how completion or state is observed — "shared surface" names implementers but tells a caller nothing. A test's comment states the behavior it pins, leading with the user-visible functionality, so a future reader knows what broke when it goes red. An encoding or wire-format comment states the measured code-to-value mapping ("nibbles are 4-bit two's complement: 0x8->-8 .. 0xF->-1"), never a mashed-up construction narrative ("sign bit plus 3-bit two's complement").
- <!-- CC-17 --> **Test comments state the invariant plus why the setup forces it.** Good: "destroys while iterating: its searcher must stay open for all 5 steps (2 steps did not catch the early close)" — the parenthetical justifies the test shape, why 5 and not 2. Bad: incident narration ("the second write is what closes") tells the story of a rejected attempt, not what the test pins. State the invariant first.
- <!-- CC-13 --> **Write function comments in the imperative: what it does, what it returns, what the caller must do.** ("Return false if it did not block within 2s. The caller must still join it.") No noun phrases joined by semicolons ("Pin the calling thread on @cpu; 0 or an errno"). A design or memory-ordering comment may run long — with labels such as (A) and (B) — but its sentences stay short and plain.

- **"Name the actor" (see §1) applies to comments too, not just changelogs.** "The caller" is a guess about which function; naming it is a claim a reader can go verify.

## 3. Contrast with generic LLM output (do NOT do these)
<!-- CL-13 -->

These apply to both changelogs and comments; kept here because they are most often violated in prose.

- **No redundant comments restating the code** ("// increment counter"). Comment only the non-obvious why.
- **No hedging filler:** "Note that", "Importantly", "It's worth noting", "Keep in mind". State facts directly.
- **No marketing adjectives** ("robust", "powerful", "seamless", "comprehensive", "elegant"). Quantify effects, don't praise them.
- **Lists are for parallel items, prose for everything else.** Test cases with their failures, requirements, per-patch entries — each item on its own line, each naming its own mapping — never chained with semicolons, never "each case passes from the fix it covers." One intro sentence says what the list lists, never a bare list after a paragraph. Anything else stays prose: a list is for items the reader must match one-to-one, not a way to dodge paragraph structure.
- **No em-dash sprinkling.** Periods and short sentences; parentheses for asides.
- **No recap paragraphs** ("In summary, this change.."). End on the effect or a trailer.
- **No mixed verb tense.** Describe the code's current behavior consistently in the present ("does", "turns"); don't drift into past ("did so") or call present code the "original" version. (validation 2026-07-01, David Hildenbrand review.)
- **No vague justification.** Not "improves performance" — give a number, a workload, a before/after.
- **No double negatives.** "not X and not Y," "doesn't not do Z," "not uncommon" force the reader to invert two negations to find the actual meaning. State the positive condition directly: "only when X" not "not unless X"; "still holds" not "doesn't not hold"; "rare" not "not uncommon."
- **No over-explaining a simple point in a comment.** If the why fits in one line, don't write five; trim to the shortest form that still conveys the reasoning. Long-but-true comments are still slop. (validation 2026-07-01, Lorenzo review of the PG_has_hwpoisoned fix.)
- **No templated Pros/Cons scaffolding.** Structure follows the actual problem→fix logic.
- **No hyper-formal tone.** Plain, occasionally dry/wry; first person ("we", "I") appears naturally.
- **No inferable boilerplate.** Skip "No functional change." on an obvious rename, "no caller yet / wired up in the next patch" status notes, a paragraph narrating a signature or type change the diff already shows, and one re-explaining what a new function's own doc comment already says. Say why something changed, not that it changed.
- **No ornate verbs** (honour, drive, convey, re-derive). Use plain ones and name who acts ("the caller uses X"; "X is passed on to the page fault code").
- <!-- CL-43 --> **No abstractions doing human verbs.** When the subject reads, sees, asks, lends, carries, proves, answers, keeps, or refuses, rewrite with the code or the reader as subject. A metaphor that explains (rides, threads, warmed) goes unless no plain version says the same thing. Extends the ornate-verbs rule from words to sentences.
- **No verbose operational detail in code comments.** Keep comments to 1–2 lines stating the invariant, not the history. Drop PIDs, hostnames, FD counts, CPU %, dates, and crash narratives from source; put those in the commit message. (matches Matthew Wilcox "drop redundant comment" Message-ID ak0sOv4UN1ug9-cN@casper.infradead.org 2026-07-07 and Lorenzo v2 comment updates, lore lkml.)
- <!-- CL-14 --> **No internal identifiers in changelogs or comments.** No internal agent/bot nicknames, no private syzkaller bucket hashes without public syzbot context, no internal branch names, no vendor ticket IDs, no private hostnames or build IDs. Upstream reviewers lack that context; it reads as noise or self-promotion. Use generic phrasing — "syzkaller triggers", "KASAN reports", "tested on v6.15-rc1" — and put machine-readable provenance in trailers (Reported-by, Link), not in prose.
- **No invented facts, numbers, or commit hashes.** Every claim must be sourced this session; if unsourced, delete or mark TODO. Do not hallucinate benchmark results, performance deltas, oops traces, or Fixes: hashes. This is a hard rule, not just a style preference.
