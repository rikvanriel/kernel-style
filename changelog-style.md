# Changelog and code comment style

Concrete rules for Linux kernel commit messages and source comments, distilled from hand-written commits 2012–2026 and maintainer edits of AI drafts. Load this when you are writing or reviewing a patch changelog or adding comments. For code structure rules (helpers, function length, early return) see `kernel-style.md` §3. For principles behind the rules see `kernel-readability-principles.md`. For LLM tells checklist see `llm-tells-checklist.md`.

## 0. Factual integrity — never invent, always verify
Canonical: [](./kernel-style.md#0-factual-integrity--never-invent-always-verify) (R0-1..R0-6) per CONTRIBUTING §2 one-source-of-truth. This section is non-canonical summary + changelog-specific tool pointers only.

- See canonical R0-1..R0-6 in kernel-style.md. In changelog context additionally:
- <!-- R0-3-CH --> Verify scope, files touched, symptom, root cause, fix mechanism, performance delta, `Fixes:` hash, `Link:` URL, `Reported-by:` name against diff this session — not from memory.
- <!-- R0-5-CH --> Paste raw artifact verbatim: oops splat, benchmark table, `git log --oneline`, `perf stat` — literal block then explanation. Checks: `git show <hash>` exists, lore/syzbot link resolves.
- <!-- R0-6-CH --> Pre-write verification gate: run `/kreview` (setup in [review-prompts.md](./review-prompts.md)), `scripts/checkpatch.pl`, `git log --oneline -- <path>`, benchmark, then write. Treat unverified prose as bug on par with wrong code. CI helper: `scripts/lint-changelog.py` checks paragraph caps, Fixes+Cc pairing, banned phrases.

## 1. Changelog / commit message
- <!-- CL-10 --> **Subject: `subsystem: lowercase imperative summary`.** Lowercase after the colon, no trailing period, imperative mood. (e.g. `1aa43598c03b` "mm: remove unnecessary calls to lru_add_drain"; `434247637c66` "bpf: use kvzmalloc to allocate BPF verifier environment"). x86/tip commits capitalize the first word per maintainer convention (e.g. `209954cbc7d0` "x86/mm/tlb: Update mm_cpumask lazily") — match the subsystem's existing style, not a fixed rule.
- <!-- CL-10b --> **Check git history for prevailing subject prefix before choosing yours.** Run `git log --oneline -- <path>` or `git log --oneline --grep <subsystem>` to see what prefix prior commits touching that file actually use, and match it. Do not invent new subsystem token when established one exists — e.g. `kernel/trace/fprobe.c` history uses `tracing/fprobe:` or `fprobe:`, never `trace/fprobe:`, so use prevailing form even if directory is `kernel/trace/`. Consistency across history matters more than literal directory name.
- <!-- CL-10c --> **Use comma-joined multi-subsystem prefixes when a change spans areas.** A common habit: `mm,vmscan:`, `ipc,sem:`, `mm,thp,shmem:`, `mm,madvise,hugetlb:` — no space after commas. (e.g. `8ebe0a5eaaeb`, `da27f796a832`).
- <!-- CL-10d --> **Subject must reflect primary impact, not cleanup label.** If change fixes race, queue stop, data loss, corruption, don't hide as "track credits" or "cleanup". Rephrase to "fix blocked-ring race permanently stopping queue" per Arend van Spriel `<d5b7a4a8-532f-47c7-a883-036d5cc81a90@broadcom.com>` brcm80211 2026-07-31. Subject describes what code does after patch, not that it fixes.
- <!-- CL-20 --> **Open the body with the problem or current behavior in plain present tense.** State what the code does today and why that's wrong, before the fix. (e.g. `e9868505987a`; `32d4f4b782bb` opens by naming the offending commit and the bug it introduced).
- <!-- CL-21 --> **Keep verb tense consistent — describe the code's current behavior in the present throughout.** If the code does X today, write "copies", "does so", "turns" — don't drift into past tense ("did so") mid-paragraph, and don't call the present code the "original" version (say "the call site"/"here", not "the original call site"). Mixing tenses makes a reviewer unsure whether you mean current behavior or history.
- <!-- CL-22 --> **Lead a bugfix with the real-world scenario and user-visible symptom, not the code mechanism.** Say who triggers it and what breaks, then descend into internals. (e.g. `2820b0f09be9` opens "Malloc libraries, like jemalloc and tcalloc, take decisions on when to call madvise.." and builds to a SIGBUS kill — it does NOT open with "zap_page_range_single fails to take i_mmap_rwsem").
- <!-- CL-23 --> **For a race, draw the interleaving as an ASCII `CPU 1 / CPU 2` diagram.** A common device. (e.g. `2820b0f09be9`).
- <!-- CL-24 --> **Match changelog length to change size.** A simple improvement gets ~3 tight paragraphs; don't walk through every code path. Bug fixes with a subtle race earn more. (e.g. `efa7df3e3bb5` is 3 short paragraphs — lead with the action "Align larger anonymous mappings..", then the qualitative benefit "better TLB hit rates and execution time", no path-by-path breakdown).
- **For a simple improvement, leading with the action then the benefit is fine** (problem-first is for bug fixes). (e.g. `efa7df3e3bb5`).
- <!-- CL-25 --> **Structure: problem → cause → fix → effect, as short prose paragraphs.** Typically 3–6 paragraphs of 2–4 sentences each. The fix paragraph often starts with the imperative verb ("Avoid the softlockup..", "Take the hugetlb_lock before.."). (e.g. `5cbcb62dddf5`, `12df140f0bdf`).
- <!-- CL-26 --> **Explain WHY far more than WHAT; justify with data, repro, or reasoning.** Quantify the effect with real numbers when available — before/after tables, percentages, timings. (e.g. `e1e4cfd01a6e` throughput table 1560→4720 MB/s; `209954cbc7d0` "Before: ~4.5s After: ~4.2s"; `da27f796a832` "from 6 minutes, to a little over 1 second").
- <!-- CL-26b --> **More about motivations than implementation details.** Lead with why old behavior was costly — user-visible symptom, spec violation, regression, or risk — not how you fixed it. Say what now happens for users or hardware, not what diff already shows.
- <!-- CL-27 --> **Paste the raw artifact verbatim; don't just describe it.** Show the actual oops/WARNING/splat with call trace, the reproducer command, or a before/after benchmark table — indented as a literal block — then explain it below. For a complex splat, annotate it with `1)` `2)` `3)` markers the prose refers to, or add `// file:line` comments at end of call trace lines as a clarifying aid provided the original function+offset text is preserved verbatim — line number annotations are allowed because they help reviewers navigate source without changing artifact meaning. Letting the reviewer see what you saw lets them verify the fix without the thread. (composite: Dan Williams `101c268bd2f3` annotated splat; Mel Gorman `09a913a7a947` benchmark table; Breno Leitao `62adf8c290f2` `time` before/after.)
- <!-- CL-28 --> **If the bug produces a kernel message, the changelog MUST include it verbatim.** For any bugfix where the kernel emits a message — KASAN/UBSAN/KFENCE report, `WARNING:`/`BUG:`, oops splat, `INFO: task hung`/soft-lockup/RCU-stall, lockdep splat, `kmemleak` unreferenced-object dump, `Call Trace` — paste the real message as an indented literal block, then explain it. Prose that only names or paraphrases the symptom ("triggers a slab-use-after-free in __up_read") is not enough; the reviewer must see the literal report. Trim register/hex-dump/memory-state noise if long, but keep the signature line, the crashing `Call Trace`, and (for UAF) the Allocated-by/Freed-by stacks. Do not embed a message you did not capture this session — if you only have a different signature than the one your prose describes, paste what you have and reconcile the prose, never fabricate the matching splat (rule 0).
- **Bound the scope and name your own weaknesses.** State explicitly what the patch does NOT do, and call out any remaining weakness, limitation, or small regression before a reviewer finds it ("the keen reader will notice..", "the main weakness is.."). It builds trust and pre-empts review churn. (composite: Johannes Weiner `e3aa7df331bc`; Mel Gorman `8d58802fc9de`; Vlastimil Babka `fc0c8f9089c2`.)
- <!-- CL-30 --> **For concurrency, locking, lifetime, bounds, and double-free fixes, add a safety paragraph.** After problem→cause→fix, explain why the fix should be safe: what lock protects the racing store, what lifetime or refcount prevents reuse, how TOCTOU is closed, or why allocation size now matches validation size. Name the lock or configfs semaphore (`down_write(&nvmet_config_sem)` deletes old controllers), the snapshot field (`ctrl->max_qid` immutable after creation), and what cannot race after the fix. Write "should be safe because..." not "is safe because...", since patches can overlook paths. This paragraph is intentionally verifiable in review — reviewers check the lock, snapshot, or free path you name. (example: nvmet `max_qid` fix `eae699c90e4b` paragraph: "This change should be safe because configfs qid_max store holds down_write(&nvmet_config_sem), updates subsys->max_qid, then deletes all existing controllers. New controllers snapshot the new value and allocate matching arrays. The snapshot in ctrl is immutable after creation, so no extra locking should be needed for readers.")
- <!-- CL-31 --> **For every syzkaller/syzbot fix, describe how the bug can happen and verify the chain.** If the report includes a reproducer, follow what the reproducer does in order, mapping each syscall/ioctl to kernel file:function. If there is no reproducer, build a concise chain of 2-4 sentences citing file:function per step: what can set flag or grow limit (e.g. `fbcon.c:fbcon_font_set` sets `hi_font_mask`, `configfs.c:attr_qid_max_store` grows `max_qid` under `down_write`), what retains stale data or old allocation (screen buffer retains glyph with high bit via `vt.c:screen_glyph`, controller keeps old small `sqs` array allocated in `core.c:nvmet_alloc_ctrl`), how buggy path differs from sister site that already checks (e.g. `bit_putcs_aligned()` at `18c4ef4e765a` clamps `ch >= charcount`, `bit_cursor()` does not; `nvmet_execute_io_connect()` validated live large but deref used old small array), and concrete OOB example (`qid=2` past 16-byte alloc, or glyph 257 past 256-glyph `fontdata_8x16+0x1010`). Keep under 70 words, one over-50 allowed. This chain is mandatory and kverify checks each file:function exists and that sister site indeed has the clamp.
- **Pre-empt the "why not fix it in the obvious place?" question.** When the fix could plausibly belong in a more obvious or upstream function, say in the changelog why that path does not or cannot handle the case (e.g. it is best-effort and can leave the bad state behind), so a reviewer does not have to ask.
- **Prefer prose to bullet lists.** Bullets appear only when quoting structured external results. Default is narrative paragraphs.
- **Trailers:** `Fixes:` for bugfixes, `Cc: <stable@..>` for user-visible fixes, `Reported-by:`/`Suggested-by:`/`Tested-by:` to credit, `Link:` to the lore posting. (e.g. `a371d558e6f3`; `da27f796a832` Suggested-by Al Viro; `1aa43598c03b` Link: footnotes).
- **Use b4 trailers to manage tags, thank reviewers explicitly in cover letter.** Lorenzo v2 cover: "Updated tags (thanks to everyone and b4 trailers -u -F! ;)" (Message-ID 20260710-b4-pre-scalable-cow-v2-0-2a5aa403d977@kernel.org 2026-07-10, lore lkml).
- **Trim Cc and To lists to relevant maintainers; don't trust b4 auto-expansion blindly.** Lorenzo notes "let b4 add recipients unlike the 1st where I trimmed. Any v3 will be trimmed again" (Message-ID alHjzZxfXOTMOC4I@lucifer 2026-07-11, lore lkml). Keep Cc focused.
- **Keep patches focused; drop unrelated hunks on request.** Reviewer: "This change is not related; please drop it." (Matthew Wilcox, Message-ID ak0sOv4UN1ug9-cN@casper.infradead.org 2026-07-07, lore lkml). Split unrelated cleanups to separate series or drop.
- <!-- CL-11 --> **If the patch has a `Fixes:` footer, add a `Cc: stable@vger.kernel.org` footer too.** A `Fixes:` tag marks the bug as worth backporting, so the stable trees need to see it; pair the two by default (checkable: `Fixes:` present but no `Cc: stable` is a red flag).
- **Add `Assisted-by:` when a coding tool did non-trivial work; the tool never signs off.** Advanced-tool use must be acknowledged — omitting it "may impede the acceptance of your work" (`Documentation/process/submitting-patches.rst`; tag spec in `Documentation/process/coding-assistants.rst`). Format `Assisted-by: AGENT_NAME:MODEL_VERSION [TOOL]`, e.g. `Assisted-by: Claude:claude-opus-4-8 syzkaller`, `Assisted-by: Hermes:muse-spark-1.2 syzkaller`, `Assisted-by: Gemini:gemini-3-pro`. AGENT_NAME is harness/framework (Claude, Hermes, Codex per coding-assistants.rst), not provider. Use public product names. List only public analysis tools (coccinelle sparse smatch syzkaller), never internal-only tooling. Multiple Assisted-by lines allowed, one per model, ordered by contribution weight. An AI agent MUST NOT add its own Signed-off-by — only human SOB certifies DCO.
- **Disclose meaningful tool assistance in the changelog, not just the trailer.** If a tool *found* the bug, say so in the changelog — it credits the tool and helps others find it; for substantial generation, note what the tool did and potentially script input (e.g. the Coccinelle source). Trivial use is out of scope and needs no tag: spelling/grammar fixes, identifier/boilerplate completion, mechanical renames, reformatting (clang-format/Lindent/rustfmt). If in doubt, disclose.
- **Credit people in the body by name when an idea or report came from them.** (e.g. `da27f796a832` "Thanks to Al Viro for the suggestion"; `187df5dde943` "Hugh pointed out that..").
- **Tone: calm, factual, engineer-to-engineer.** Occasional dry understatement, never marketing. (e.g. `434247637c66` "Admittedly this is not a very common case.. but it's a simple enough fix").
- <!-- CL-14 --> <!-- CL-14-CH --> **Write for the upstream audience, not your internal tooling.** A changelog is read by maintainers who have never seen your CI dashboard, internal bot nicknames, private branch names, or vendor ticket systems. Include only information that helps an upstream reviewer understand, reproduce, and verify the fix. Strip internal identifiers that carry no meaning outside your environment — internal agent or bot nicknames ("analyzed by internal-agent-1"), internal syzkaller or CI bucket hashes without a public syzkaller or syzbot link, internal git branch names (`internal-fixes-2026-07-15`), internal hostnames, PIDs from private test runs unless they illustrate the bug mechanism, build IDs from private trees, Phabricator or Jira IDs, etc. Replace them with generic, reproducible descriptions: "syzkaller triggers..", "KASAN reports..", "reproducer available at syzbot <link>..", "tested on v6.15-rc1". If an internal tool found the bug, credit it generically in prose ("found by syzkaller") and via Reported-by or Assisted-by trailer using the public provider:model format, not by naming the private instance. Code comments get even less context than changelogs — never mention internal dashboards, bucket IDs, or agent names in source; put that in the commit message if at all, and even there prefer generic.
- **State the reason once; don't sell the change or re-argue it.** Give the rationale plainly, a single time — never argue that the change is good, that the old form "reads oddly," or reorder a later, otherwise-neutral section (e.g. benchmark results) just to lean on a point already made. (Cut from the get_user_page_lookup_vma rename: "The 'remote' in the name describes the mm, not what the helper does, and reads oddly next to get_user_pages_remote(). Name it for its action.")
- **Active voice; name the actor; plain verbs.** Prefer "The caller uses FOLL_VMA_LOCK to indicate it holds a per-VMA lock" over "the lock the caller holds is conveyed by a flag"; "hard codes use of the mmap_lock, and does a lookup of the VMA" over "takes and drops the mmap lock itself and re-derives the VMA". (edit of AI draft, get_user_page_vma series 2026)
- **One idea per paragraph; break a running block apart.** The problem, the "existing API doesn't fit" note, and the resulting behavior each get their own short paragraph rather than one dense block. (edit of AI draft, same series)
- <!-- CL-12 --> **Cap paragraph length: at most one paragraph may exceed 50 words, and none may exceed 70.** The one allowance is for content that genuinely cannot be split; a second over-long paragraph means the changelog wants restructuring, not a longer allowance. Applies to both changelogs and code comments. A checkable backstop for "one idea per paragraph": a paragraph over the limit is a signal to split it, not to pad it to 70.
- **Merging two related clauses under the cap beats splitting them just to satisfy "one idea per paragraph."** A paragraph break has a real cost — the next paragraph re-establishes subject and context from scratch — so only pay it when the cap forces it or the two halves are genuinely separate, independently-verifiable claims. If two adjacent short paragraphs still fit under 50 words joined by a connective (since, so, then, --), join them; that is the shorter form, not a less clear one.
- **Before finalizing, run a compression pass over the whole changelog, checking each paragraph against three questions.** (1) Does it restate what a code comment added or touched by the same diff already says? If so, cut it to nothing or a single clause — the reviewer has the comment right there. (2) Does it gloss an already-obvious value (a sentinel, an enum, a self-explanatory name) by restating its meaning in English? Cut the gloss. (3) Do two adjacent paragraphs describe sequential sub-steps of the same single change that a connective could join under the cap? Join them. What survives this pass should be only the paragraphs carrying a genuinely distinct, independently-verifiable claim — a correctness nuance, a safety argument, a separately-measured effect — that a reviewer needs to check on its own; don't merge those away just to hit a length target.
- **Forward-reference a later patch for purpose, not status.** Keep "cleans up the name space for adding a get_user_page_vma() variant" (why the patch exists); drop "no caller uses it yet; switched to it in the next patch" (bookkeeping the reader already sees).
- **Justify a prep patch on its own terms; never describe a later patch's behavior as this patch's motivation.** Open with the problem that exists *now*, in present tense, the way the accepted x86 sibling does ("__access_remote_vm() reads another process's memory under the mmap lock .. that lock is contended"), not with what a follow-up will do ("Later in this series __access_remote_vm() untags the remote address without holding the mmap lock"). At the prep patch that later behavior does not exist yet, so stating it as the reason misleads a reviewer reading the patch in order. Forward-reference the later patch only for purpose (why the helper is added), never as if it were current behavior.

## 2. Code comments
- **Comment the WHY: hardware behavior, locking, ordering, lifetime, subtle invariants — never restate the code.** (e.g. `b7aa05cbdc52` INVLPGB ordering/flag semantics; `209954cbc7d0` "Atomic writes to mm_cpumask can be expensive under contention. The CPU will be removed lazily at TLB flush time.").
- **Density is low and purposeful.** Most lines uncommented; comments cluster where reasoning is non-obvious (a new helper, a tricky branch, a race). Obvious code gets none.
- **Keep a comment as short as the point allows — one or two lines for a simple invariant, not a paragraph.** Even when every line is accurate, padding an obvious placement/ordering rule into a multi-line explanation reads as LLM slop. Say the why in the fewest words and stop.
- **Same paragraph cap as changelogs: at least 90% of comment paragraphs 50 words or fewer, at most 10% up to 70 words, never beyond.**
- **For multi-branch helpers, give each branch a one-line rationale.** (e.g. `6db2526c1d69` `should_flush_tlb()`: "/* Lazy TLB will get flushed at the next context switch. */", "/* No mm means kernel memory flush. */", "/* In cpumask, but not the loaded mm? Periodically remove by flushing. */").
- **Break up very large conditionals and comment each outcome.** Lorenzo v2 14/33: "Break up the existing very large conditional, add comments and use.." (Message-ID 20260710-b4-pre-scalable-cow-v2-14-2a5aa403d977@kernel.org 2026-07-10). Prefer early return or helper split over dense if-else chains.
- **ASCII diagrams welcome for complex range or state adjustments, under 60 columns plain ASCII.** Lorenzo v2 15/33: "Add comments with ASCII diagrams to describe what we're doing" (Message-ID 20260710-b4-pre-scalable-cow-v2-15-2a5aa403d977@kernel.org). No Unicode box drawing.
- **Cross-reference other comments rather than duplicate explanation.** Lorenzo v2 17/33: "We refer the reader to the comment for vma_start_pgoff() so we don't.." (Message-ID 20260710-b4-pre-scalable-cow-v2-17-2a5aa403d977@kernel.org). One source of truth per invariant.
- **Improve comment language opportunistically when touching code, keep it concise.** Lorenzo v2 30/33: "While we're here, slightly improve the language of the comment describing" (Message-ID 20260710-b4-pre-scalable-cow-v2-30-2a5aa403d977@kernel.org).
- **Block comments above the function/decl; short notes inline or just above the line.** Full sentences, capitalized, ending with a period. (e.g. `f35b5d7d676e` "/* Ensures that larger anonymous mappings are THP aligned. */").
- **Do not comment function declarations in header files; document at the definition.** A bare prototype in a `.h` gets no descriptive comment — put the explanation in a block comment above the function body in the `.c` file, so there is one source of truth that cannot drift out of sync with the code. (Kerneldoc `/** */` for an exported API is the deliberate exception, and even that lives above the definition, not the prototype.)
- **Code comments are for upstream readers too — no internal identifiers in source.** Never mention internal dashboards, CI bucket hashes, agent or bot nicknames, private branch names, internal hostnames, or vendor ticket IDs in a `/* */` or `//` comment. Those rot the moment code leaves your tree and confuse reviewers who lack that context. Put operational provenance in the commit message if needed, and even there prefer generic phrasing per the changelog audience rule above.
- **Block comments are typically 2–8 lines of plain wrapped prose**, occasionally with a worded example list. (e.g. `b7aa05cbdc52`).
- **Personality is allowed in comments when it conveys real information.** (e.g. `b7aa05cbdc52` "/* Some compilers (I'm looking at you clang!) simply can't do DCE */").
- **Introduce a new helper by relating it to the family it resembles, then name the one key difference.** Orients a kernel reader faster than describing the mechanics from scratch. (Prefer "Simplified get_user_page* loop, which only walks page tables because we already have the VMA" over a from-scratch "walks the tables with follow_page_mask() and faults one in…"; get_user_page_vma doc comment 2026)
- **Don't frame current behavior as "instead of" an alternative that isn't visible in the code, even without naming it.** A comment saying a loop does X "instead of restarting the walk at each boundary" asks the reader to already hold a design in mind that no longer exists to read. State what the code does and, if needed, why it's safe; save "why this beats what came before" for the changelog, which is inherently a before/after document. (Cut from a loop comment that implicitly compared against a removed per-call design: "Walk every PTE from @address to @end" replaced "...in one call, instead of restarting the walk... at each folio boundary.")
- **Reach for an established systems-programming term for a common pattern instead of re-describing the mechanism, and name the specific function that completes the other half of the contract.** "Short read" (return fewer than requested, non-error, caller retries) says in two words what a bespoke description takes a sentence to say, and naming the actual function makes the claim checkable. Prefer "a failure partway through results in a short read; __get_user_pages() retrying the read will get the error" over "the walk stops and returns what it has; the caller re-issues from there."
- **"Name the actor" (see §1) applies to comments too, not just changelogs.** "The caller" is a guess about which function; naming it is a claim a reader can go verify.

## 3. Contrast with generic LLM output (do NOT do these)
<!-- CL-13 -->

These apply to both changelogs and comments; kept here because they are most often violated in prose.

- **No redundant comments restating the code** ("// increment counter"). Comment only the non-obvious why.
- **No hedging filler:** "Note that", "Importantly", "It's worth noting", "Keep in mind". State facts directly.
- **No marketing adjectives** ("robust", "powerful", "seamless", "comprehensive", "elegant"). Quantify effects, don't praise them.
- **No over-bulleting.** Paragraphs by default; bullets only for quoted data.
- **No em-dash sprinkling.** Periods and short sentences; parentheses for asides.
- **No recap paragraphs** ("In summary, this change.."). End on the effect or a trailer.
- **No mixed verb tense.** Describe the code's current behavior consistently in the present ("does", "turns"); don't drift into past ("did so") or call present code the "original" version. (validation 2026-07-01, David Hildenbrand review.)
- **No vague justification.** Not "improves performance" — give a number, a workload, a before/after.
- **No double negatives.** "not X and not Y," "doesn't not do Z," "not uncommon" force the reader to invert two negations to find the actual meaning. State the positive condition directly: "only when X" not "not unless X"; "still holds" not "doesn't not hold"; "rare" not "not uncommon."
- **No over-explaining a simple point in a comment.** If the why fits in one line, don't write five; trim to the shortest form that still conveys the reasoning. Long-but-true comments are still slop. (validation 2026-07-01, Lorenzo review of the PG_has_hwpoisoned fix.)
- **No templated Pros/Cons scaffolding.** Structure follows the actual problem→fix logic.
- **No hyper-formal tone.** Plain, occasionally dry/wry; first person ("we", "I") appears naturally.
- **No inferable boilerplate.** Skip "No functional change." on an obvious rename, "no caller yet / wired up in the next patch" status notes, a paragraph narrating a signature or type change the diff already shows, and one re-explaining what a new function's own doc comment already says. Say why something changed, not that it changed.
- **No ornate verbs** (honour, drive, convey, re-derive). Use plain ones and name who acts ("the caller uses X"; "X is passed on to the page fault code").
- **No verbose operational detail in code comments.** Keep comments to 1–2 lines stating the invariant, not the history. Drop PIDs, hostnames, FD counts, CPU %, dates, and crash narratives from source; put those in the commit message. (matches Matthew Wilcox "drop redundant comment" Message-ID ak0sOv4UN1ug9-cN@casper.infradead.org 2026-07-07 and Lorenzo v2 comment updates, lore lkml.)
- <!-- CL-14 --> **No internal identifiers in changelogs or comments.** No internal agent/bot nicknames, no private syzkaller bucket hashes without public syzbot context, no internal branch names, no vendor ticket IDs, no private hostnames or build IDs. Upstream reviewers lack that context; it reads as noise or self-promotion. Use generic phrasing — "syzkaller triggers", "KASAN reports", "tested on v6.15-rc1" — and put machine-readable provenance in trailers (Reported-by, Link, Assisted-by), not in prose.
- **No invented facts, numbers, or commit hashes.** Every claim must be sourced this session; if unsourced, delete or mark TODO. Do not hallucinate benchmark results, performance deltas, oops traces, or Fixes: hashes. This is a hard rule, not just a style preference.

## Anchors (verbatim)

> — tight problem→fix body, `4eb919825e6c`
> "On busy multi-threaded workloads, there can be significant contention on the mm_cpumask at context switch time."
> — changelog opening, `209954cbc7d0`
> "Admittedly this is not a very common case, and only happens on systems where memory has already been squeezed close to the limit, but this does not seem like much of a hot path, and it's a simple enough fix."
> — dry justification tone, `434247637c66`
> `/* In cpumask, but not the loaded mm? Periodically remove by flushing. */`
> — per-branch why-comment in a predicate helper, `6db2526c1d69`
